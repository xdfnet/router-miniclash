# 巡检清单与汇报方案

手动巡检的标准流程。每个项目有固定判据，命中异常才需要动作；全部正常时
不需要逐项汇报（见文末汇报模板）。

一条命令跑完全部取数：`./scripts/inspect.sh`（自动执行 1~8 项并输出结构化结果，
第 9 项需人工判读）。

---

## 巡检项目

### 1. 服务存活
- **取数**：`/etc/init.d/miniclash status`；`/proc/<pid>/stat` 算启动时刻
- **判据**：状态「运行中」；连续运行时长 ≥ 24h（突然归零 = 崩溃重启）
- **异常处置**：查 `miniclash.log` 尾部的「已停止/已启动」配对，定位重启原因

### 2. 配置有效
- **取数**：`mihomo -t -d /etc/miniclash -f /etc/miniclash/config.yaml`；
  `rules:` 前 12 条；`nameserver-policy` 段
- **判据**：试读通过；注入规则按预期在前（DIRECT 例外、apple/微软走代理）
- **异常处置**：注入顺序错位会吞掉后续全部规则，表现为 `proxy [自动优选...] not found`；
  改 init.d 的 `EXTRA` 块后必须 `mihomo -t` 再 restart

### 3. 选优健康
- **取数**：`uci get miniclash.core.node`；`/etc/miniclash/judge.log` 近 12 轮 + 全量裁决类型分布；
  `/etc/miniclash/guard.log`（故障自愈记录）；`/tmp/miniclash_rank`（当前带宽排名）；
  `/tmp/miniclash_bandwidth.total`（探测累计流量）
- **判据**：当前节点与最近裁决一致；judge **每 15 分钟一轮**无断档；
  裁决以「保持」为主，少量「切换」属正常；探测累计流量应稳定在 ~1.5GB/天量级（每轮测全部 16 个节点 × 1MB）
- **异常处置**：频繁切换 = 两个节点**带宽**接近或节点劣化，看 judge.log 的带宽差值
  （判据是真实下载带宽，不是延迟——见 [单池择优](pool-selection.md)）；
  裁决断档 = judge cron 没跑，查 init.d 的 cron 注册；
  guard.log 频繁报"当前节点不通" = 节点真在挂，或入口 IP 被整段阻断（见 README 排障）；
  探测流量异常增长 = 样本量或测速次数出了问题

### 4. 流量与套餐
- **取数**：`./scripts/traffic.sh`
- **判据**：剩余流量与天数匹配（剩余 GB / 剩余天数 ≥ 日常均耗）；未过期
- **异常处置**：余量骤降 = 有异常大流量（视频/更新/爬虫），转第 5 项定位

### 5. 流量走向
- **取数**：`./scripts/traffic-audit.sh`
- **判据**：直连占比 > 代理占比（国内流量不该大量走代理）；
  代理桶 Top 域以「确需代理的境外服务」为主
- **异常处置**：见第 9 项

### 6. 告警归因
- **取数**：`miniclash.log` 的 `level=warning` 按错误类型与 `match` 规则聚合
- **判据**：能按已知模式归类即为正常——
  - `connection refused` 127.0.0.1:14013/14016/14019（微信桌面端本地服务）
    → **不是正常现象**：说明 fake-ip 又把 `localhost.weixin.qq.com` 劫走了，
    查 dnsmasq drop-in 的 `host-record=localhost.weixin.qq.com,127.0.0.1` 是否还在
  - `context deadline exceeded` / `EOF` / `i/o timeout` → 机场入口间歇阻断，短时自愈
  - `dns resolve failed` → 确认目标域，多为子域本就不解析
  - `context canceled` → 上游主动取消
  - `dial tcp 17.x.x.x:5223 i/o timeout` → Apple 推送。订阅自带 `IP-CIDR,17.0.0.0/8,DIRECT`
    排在注入的 `DOMAIN-SUFFIX,apple.com` 之前，先命中直连；客户端用真实 IP 时
    域名规则也匹配不到 → 推送超时但不致命，属已知现象
- **异常处置**：出现归不了类的类型，或某类型条数较上轮成倍增长 → 展开逐条看

### 7. 出网实测
- **取数**：Mac 侧 `curl` 测四条路径——代理域（github.com、hf-mirror.com）、
  直连域（www.baidu.com、registry.npmmirror.com）
- **判据**：全部 http=200；代理域解析到 fake-ip 段 `198.18.0.0/16`
- **额外必测**：`https://dl.google.com/chrome/mac/universal/stable/GGRO/googlechrome.dmg` 走 3MB Range，
  应 > 1MB/s（该域名强制 DIRECT，走国内 CDN；2026-10-29 修规则前只有 0.1MB/s）
- **例外**：只有**用路由器 DNS 的客户端**才拿到 fake-ip。客户端自己手工配了外部 DNS
  （如 Mac Wi-Fi 手工设 223.5.5.5/114.114.114.114）时解析到真实 IP，
  该机流量在 mihomo 里 `host` 为空 → 只命中 IP/GeoIP 类规则，域名规则对其失效。
  这时「ip 不是 198.18.x」不是故障，是客户端配置问题
- **异常处置**：注意重启后 15 秒内测会假失败（代理连接未预热），要复测

### 8. 规则库时效
- **取数**：`.mihomo-version` vs GitHub latest；路由器上
  `Country.mmdb` / `cn.mrs` 的 md5 vs 上游
- **判据**：内核版本 = 上游 latest
- **异常处置**：内核有新版 → `./scripts/update-kernel.sh`；
  规则库过期 → 备份后上传，`mihomo -t` 通过再 restart

### 9. 干预候选（自动：兜底代理域名 vs 直连对照）
- **取数**：`./scripts/domain-candidates.sh [候选数，默认 5] [天数，默认 3]`（巡检自动跑）
  —— 数据源是第 5 项的"兜底走代理"桶（没命中任何专门规则、被动走代理的域名）
- **判据**：只有同时满足才报「候选」——
  ① 两轮直连都通（不是 000）；② 两轮直连的 HTTP 状态码一致；③ 直连状态码与代理一致
  （状态码不同 = 直连落在另一个端点，多半不是同一个服务，**不可比**）；
  ④ 直连耗时 ≤ 代理 × 0.6
- **为什么要自动跑**：靠人工翻"谁在吃代理流量"会漏——2026-10-29 实测 dl.google.com 在桶里排第 14 位，
  但直连 13MB/s vs 代理 0.1MB/s，差 100 倍，不逐个对照根本发现不了
- **异常处置**：判「候选」的域名按 [domain-rules.md](domain-rules.md) 第三节**用真实文件**复核吞吐
  （根路径只测首字节，会骗人）；确认有收益才加规则，并把结论写进 domain-rules.md。
  **没带来提速就是没收益，回滚**。已在 domain-rules.md 记录为"必须代理"的域名会自动跳过

### 9b. 复核已生效的干预（自动：规则还该留着吗）
- **取数**：`./scripts/domain-review.sh [天数，默认 7]`（巡检自动跑）——
  对 init.d EXTRA 块里的每条规则，用**真实在用的主机**（从 meter 按命中规则取）
  测直连路径与代理路径（代理路径用 mihomo global 模式实测，测完立刻切回 rule）
- **判据**（按规则走向分别解释）：
  - DIRECT 规则：代理快 ≥1.6 倍 → 建议撤销/改走代理；直连不通 → 必须改成代理
  - PROXY 规则：直连快 ≥1.6 倍 → 建议撤销/改走直连；直连不通 → 保持代理
- **两个必须记的坑**：① 裸域名常常没有 A 记录（如 `boost1.shop` 本体不解析，
  真正在用的是 `sub.`/`vercdn.boost1.shop`），拿裸域名测会误报"直连不通"；
  ② DIRECT 规则的域名在规则生效时就是走直连的，普通 curl 测到的仍是直连路径，
  比出来的"代理更快"是假的——必须用 global 模式测代理路径
- **异常处置**：⚠ 是**线索不是判决**——每条都要用真实业务流量再验一次
  （2026-10-29 复核出的两条 ⚠ 最后都维持原样，见 [domain-rules.md](domain-rules.md) 第四节）。
  真要改规则时，同一次提交里更新 domain-rules.md

### 10. 分流正确性（人工判读）
- **取数**：第 5 项的代理桶域名 → 在路由器上取真实 IP 并实测真实直连
  （实测片段见 [domain-rules.md 第三节](domain-rules.md)，那里是唯一真源；
  注意解析要只取 IPv4——`[0-9.]+` 会把 IPv6 截成 "2606" 这类碎片）
- **判据**：
  - 真实 IP 属国内段且**直连明显快于代理** → 不该走代理，加 DIRECT 规则
  - 直连不通或更慢 → 保持代理
  - 属已知有意设计（Apple 全家、微软账号域）→ 不动
- **异常处置**：加规则要同时改 init.d 的 `EXTRA` 块 + 文档，部署后实测并
  复测其余路径确认无回归。**若规则加上去没带来提速，就是没收益，回滚**
  （真实案例：gdtimg.com 加 DIRECT 后仍 2.5s，因为腾讯广告用的是境外 CDN 节点）

## 汇报模板

每次巡检按此结构汇报，正常项合并成一句，异常项必须带证据：

```
结论：<健康 / 有 N 项待处理>

异常项：
- <现象> —— 证据：<实测数据> —— 建议：<动作>
  （要飞哥定的放这里，单独列「待决策」）

正常项：<合并一行，不逐项展开>
```

汇报纪律：
- 结论先行，异常项带数字证据（延迟、字节数、条数），不贴整段日志
- 「待决策」与「已做」分开列，不要把已完成的再列成待办
- 判据不明的异常标「待查」，不猜结论
