# 跨国选优：国家之间怎么切

> 记录「自动优选」主组在**日本组 / 新加坡组**之间如何裁决：判据、测速方法、防抖、
> 流量预算。与 [组内选优](group-selection.md)（组内选哪个节点）配套，机制不同、互不干涉。

## 一、分工：谁决定什么

```
自动优选 (select)                    ← judge 只对这一层发 PUT（跨国切换）
├── 日本组 (url-test)  ── 日本1…8    ← 组内由 mihomo 内核决定（见 group-selection.md）
└── 新加坡组 (url-test) ── 新加坡1…8
```

- **judge.sh 不碰组内**，只对主组「自动优选」发一次 PUT。
- **init.d 的 watchdog 只观察不驱动**：每 60s 把 select→国家组→节点展开上报 `miniclash.core.node`。
- 组内的 url-test 每 60s 自测，`tolerance: 200` 防抖，节点挂了内核秒级自愈——跨国裁决完全不参与。

## 二、判据：真实下载带宽，不是延迟

2026-10-24 换掉了原来的延迟判据（原判据：每 5 分钟用 mihomo delay API 实测 GitHub 主站 +
githubassets(Fastly) 两地址，延迟相加打分）。

### 为什么换

| | 延迟（两地址相加，抗噪后） | 带宽（最优节点） |
|---|---|---|
| 日本 | 644ms | 226KB/s |
| 新加坡 | 587ms（快 8.8%） | 160KB/s（**日本快 41%**） |

两个判据给出**相反的答案**。根因：mihomo 的 delay API 只测建连+首字节(TTFB)，不随响应体大小
增长——2026-10-24 实测同一节点同一 URL，1MB 与 8MB 耗时完全相同，**它测不出带宽**。

原来的 20% 切换门槛也失效：抗噪后两国真实差距只有 8.8%，而单样本噪声能造出 100% 的差距
（日本在 judge.log 里于 1001~1212ms 之间乱跳）→ 切换成了随机行为，不是「稳」。

### 现在的两层判据

1. **紧急逃生（零流量、即时）**：读内核 url-test 的 `alive` 状态——内核自己每 60s 测一次，
   本地 API 读，不产生外网流量。当前国活节点 < 2 → 立刻切到活节点最多的国家，不等带宽测速。
2. **择优（带宽）**：节点分 = 该节点最近 4 次测量的**中位数**（单次噪声可达 55%）；
   国家分 = 该国节点分最高**前 2 个的平均**（活节点不足 2 个 = 不可用）；
   连续 2 次同一别国领先、**且**领先 25% → `PUT /proxies/自动优选 {"name":"X组"}`。

## 三、带宽怎么测

### 测速底座：listeners 的 pinned 端口

每个节点在 config.yaml 的 `listeners` 段有一个钉死到它的本地 HTTP 端口：

```yaml
listeners:
    - { name: probe-日本1, type: http, port: 9100, listen: 127.0.0.1, proxy: '日本1' }
```

经 `http://127.0.0.1:9100` 发出的请求**一定走日本1**，与主组当前选谁无关，也不干扰线上流量
（独立端口、独立连接）。端口↔节点映射直接读配置的 listeners 段——**配置是唯一事实来源**。

由 init.d 的 `gen_config()` 生成（端口从 9100 起按订阅节点顺序顺延）。改了节点归集规则或端口
起点，probe.sh 一侧必须同步，否则 probe 静默测不到（国家分变 0）。

### 测法（每条都是实测逼出来的）

| 做法 | 理由（2026-10-24 / 10-25 实测） |
|---|---|
| **必须串行** | 16 路并发互相抢带宽，排序完全失真：并发测日本3 第一(174K)、串行测日本1 第一(226K)；日本5 并发 30K、串行 144K |
| 样本 **1MB** | 样本太小则握手时间占比过高，测的是握手不是带宽。2026-10-25 实测：同一批节点 256KB 测出 210~240K，1MB 测出 700~1100K（差 3~5 倍）；**排序还会翻转**——256KB 下新加坡领先(238K vs 日本 224K)，1MB 下日本前两名中位数 915K 反高于新加坡 855K，按 256KB 裁决会稳定选到慢线路 |
| 节点分取**中位数** | 单次采样噪声可达 55%：日本3 连测 133K / 180K / 206K |
| 探测目标 GitHub raw MAINTAINERS | 真实业务目标、支持 Range、不触发限流（16 并发拉 codeload tarball 全部 429） |

### 轮转：每轮只测 8 个节点

每国节点按订阅顺序排成环，窗口 4 个、每轮步进 4 → **2 轮（30 分钟）覆盖该国全部 8 个节点**。
节点分取历史中位数，所以本轮没测到的节点用上一轮数据，分数依然可比。

## 四、流量预算

| 方案 | 每轮 | 频率 | 天流量 | 20 天占剩余 155GB |
|---|---|---|---|---|
| 全量 16 节点 × 128KB | 2MB | 5min | 590MB | 11.8GB / 7.6% |
| 每国 4 节点轮转 × 256KB | 2MB | 15min | 196MB | 3.9GB / 2.5% |
| **现方案：每国 4 节点轮转 × 1MB** | 9MB | **15min** | **~864MB** | 17.3GB / 11.2% |

样本从 256KB 提到 1MB 是为了不把握手当带宽（详见第三节），代价是探测流量 ×4——
仍在配额预算内（占剩余 ~0.5%/天）。实测每轮探测 ~9MB（8 节点 × 926KB + HTTP 开销），与预算一致。累计消耗记在
`/tmp/miniclash_bandwidth.total`，巡检第 3 项「带宽测速累计消耗」直接可读。

> 换样本量时必须清空 `/tmp/miniclash_bandwidth.state`（历史里混着两种尺度的 B/s，
> 中位数跨尺度平均无意义）。

## 五、防抖与状态

| 文件 | 内容 | 何时清 |
|---|---|---|
| `/tmp/miniclash_judge.state` | 防抖计数（`PENDING` / `COUNT`） | 判定「保持」或切换成功时清空 |
| `/tmp/miniclash_judge_rot.state` | 每国测速轮转指针（`ROT1` / `ROT2`） | **不清**（跟着 STATE 清会导致永远只测前 4 个节点） |
| `/tmp/miniclash_bandwidth.state` | 每节点最近 4 次带宽值 | 重启丢失（/tmp），攒够 4 次后中位数才稳 |

连续 2 次 = 30 分钟（15 分钟一轮）。margin 25%：实测两国带宽差 41%，门槛低于 25% 会被噪声
带着乱切，高于 25% 则真实劣化到 25% 以内切不动。

**开机直选（BOOT 模式）**：select 启动默认固定选第一个成员（新加坡），并非实时最优。
init.d start() 末尾以 `BOOT=1` 前台跑一次 judge，测**全部**节点、绕过双确认直接 PUT 进最优
国家（约 30s）。cron 常规轮次不带 BOOT，防抖不变。

## 六、被否决的方案

| 方案 | 否决理由 |
|---|---|
| 国家组 url-test → fallback，让 judge PUT 指定组内节点 | 实测 fallback 组不吃 PUT，组内指定是空转；且 fallback 永远选列表第一个节点，等于放弃择优 |
| 全量 16 节点 × 5 分钟一轮 | 590MB/天，占配额 7.6%，不值 |
| 缩小样本（64KB）省流量 | 样本越小噪声越大，64KB 基本只测到握手，判据直接瞎掉 |
| 单次采样直接用 | 单次噪声 55%，国家分乱跳，切换变随机行为 |

## 七、观察点

1. **探测流量**：巡检第 3 项应稳定在 ~860MB/天量级；超出说明轮转或样本出了问题。
2. **切换是否合理**：judge.log 里国家分与实际体验是否一致。若长期锁在明显更差的国家，
   先看 margin 是否过大（25%），再看每节点中位数样本够不够（满 4 次才稳）。
3. **日志格式**：`日本:192160B/s, 新加坡:221855B/s | 保持 新加坡 | 探测累计 18MB`。
   紧急逃生行形如 `日本 活节点 1(<2) | 紧急切 新加坡(活节点 6)`。

## 八、遗留问题

- ~~日本5、日本6 节点已死~~（2026-10-24 实测两地址全失败、带宽恒为 0）：
  2026-10-25 复测两节点均正常（日本5 416K/s、日本6 499K/s，1MB 样本），
  url-test 也报活（969ms / 1416ms）→ 该条已失效，节点健康会随机场调度变化，需时查。
- **组内仍是延迟判据**：国家 url-test 组按延迟选节点，而组内延迟真值只差 34ms（无区分度）、
  带宽差 5.8 倍。要让组内也按带宽择优，只能把国家组改成 select（judge PUT 可用），代价是失去
  内核自愈。见 [组内选优](group-selection.md) 第六节。
- **按需探测未做**：目前固定 15 分钟一轮。可用零流量的延迟信号做触发器（延迟异常时立刻来一轮
  全量带宽测速），平时只留低频常规测速。
- **真实流量信号未用**：`meter.sh` 每分钟已采样 `/connections`，若按代理链统计到节点维度，
  家里有下载/视频时真实吞吐就是零成本的带宽信号，可优先于主动探测。
