# 单池择优：谁当出口，自己说了算

> 记录"用哪个节点当出口"这件事的机制、判据和实测依据。
> 2026-10-29 起主组改为**单池 select**（成员就是全部节点），选谁、切换、故障自愈全部自己管，
> 内核的 url-test 不再参与选择。本文取代了原 `country-selection.md`（跨国择优）与
> `group-selection.md`（组内核 url-test）两篇——那两层结构已不存在，留着只会自己腐烂。

---

## 一、现在的结构：单池 + 脚本全权

```
自动优选 (select)        ← 唯一的组，成员就是全部 16 个节点
├── 日本1 … 日本8
└── 新加坡1 … 新加坡8
```

- **judge.sh**（cron 每 15 分钟）：实测每个节点的真实下载带宽 → 按带宽排名 → 选第一名，
  用 API `PUT` 进「自动优选」。
- **guard.sh**（watchdog 每 60 秒调一次）：探活当前节点，不通就切到排名里第一个活的。
- **init.d 的 watchdog**：调 guard.sh 自愈 + 把当前节点名上报到 `miniclash.core.node`。
- 内核只负责"按规则转发"，不参与选择。

## 二、为什么不再让内核 url-test 选（2026-10-29 实测）

内核 url-test 每 60s 对组内每个节点打一次 `generate_204`，按**延迟**选最快的。它有三个问题：

1. **延迟 ≠ 带宽**（本项目 2026-10-24 就已实测：延迟与带宽并不同向）。
2. **单样本噪声极大**。同一批 8 个新加坡节点、同一个 URL、同一天下午连测：

   | 节点 | 新加坡6 | 新加坡3 | 新加坡7 | 新加坡8 | 新加坡5 | 新加坡4 | 新加坡1 | 新加坡2 |
   |---|---|---|---|---|---|---|---|---|
   | 延迟(ms) | 480 | 547 | 891 | 977 | 1033 | 1172 | 2016 | 2770 |

   同一批节点的带宽差异是 **30KB/s ~ 1.1MB/s（36 倍）**，而延迟噪声能到 2.3 倍——
   延迟排序根本分不出谁快。
3. **实测它选中的恰是带宽最差的节点**。内核当时把「新加坡组」固定在**新加坡1**：

   | 节点 | 到 dl.google.com 的真实下载速度（串行 3MB 实测） |
   |---|---|
   | 新加坡1（内核选中） | **111 KB/s** |
   | 新加坡7 | 829 KB/s |
   | 新加坡2 | 382 KB/s |
   | 日本5 | 233 KB/s |

   也就是说，靠 url-test 选出来的出口，在实际的大文件下载上是最慢的一档。

### 顺带解决的一个老坑

原结构里"组内"归内核管、"跨国"归 judge 管，两套判据（延迟 vs 带宽）叠在一起互相打架，
而且国家清单在 `init.d` 和 `judge.sh` 两处硬编码、改一处忘另一处就会漂移。
单池之后只有**一套判据（带宽）、一个决策点（judge）、一个自愈点（guard）**。

## 三、判据：真实下载带宽

- **怎么测**：每个节点在 `config.yaml` 的 `listeners` 段有一个钉死的本地 HTTP 端口
  （`probe-<节点名>`，9100 起，只绑 127.0.0.1），经该端口下载 1MB 真实内容即得该节点的真实速度。
  配置是端口→节点的唯一事实来源，不另建映射表。
- **为什么不能用 delay API**：它只测建连+首字节（TTFB），不随响应体大小增长——
  同一节点同一 URL，1MB 与 8MB 耗时相同（2026-10-24 实测），测不出带宽。
- **样本 1MB**：256KB 把握手当带宽，且会让排序翻转（2026-10-25 实测）。
- **必须串行**：并发会互抢带宽，排序完全失真（2026-10-24 实测：并发与串行同一节点差 3 倍）。
- **抗噪**：节点分 = 最近 4 次测量的**中位数**（单次采样噪声可达 55%）。

### 切换门槛：双确认 + 25% margin，外加一条快速通道

- **常规**：连续 2 轮出现同一候选、且它比当前节点快 25% 以上才切。理由同"跨国择优"时期：
  防噪声驱动打地鼠横跳。切换会断连（在途连接重建、浏览器重连、缓存重建），
  2026-10-15 踩过 judge 测速污染内核延迟记录、导致组内每 5 分钟横跳一次的坑。
- **快速通道**：当前节点带宽掉到最优的 **1/3 以下**时，**单轮即切**，不等双确认。
  为什么单开这条：死节点有 guard.sh 兜着（60 秒粒度），但**"慢而没死"的节点只有测速能看出来**，
  按常规门槛要等 30 分钟——而"用最快的节点"正是这套机制的核心承诺，慢节点体感比死节点更常见
  （死节点断网用户立刻发现，慢节点只是"网速慢"，用户只会骂）。

## 四、故障自愈：guard.sh

单池 select 没有内核兜底（url-test 没了），所以自己写：

- **探活**：mihomo 的 delay API —— 内核用指定节点发一次真实请求，通=活。
  与 probe 的测速 URL **刻意不同**（probe 打 raw.githubusercontent 的 1MB 正文，
  guard 打 generate_204）：probe 测带宽、guard 测活着，两者互不污染读数。
- **切换**：当前节点不通 → 按 judge 写的排名文件（`/tmp/miniclash_rank`）从前往后找，
  找到第一个活的就 PUT 进去；最多试 5 个备选。
- **谁来调**：init.d 的 watchdog 每 60 秒调一次（`check_interval`），judge 每轮开头也调一次兜底。

> 注意：`alive` 字段只在内核有 url-test 组时才维护。没有 url-test 组之后，
> 节点的 alive 不可信——探活必须自己做（本项目的 `alive_of` 曾依赖内核 alive，现已废）。

## 五、流量预算

每轮测**全部 16 个节点** × 1MB ≈ 16MB/轮，15 分钟一轮 ≈ **1.5GB/天**（占剩余配额约 1%）。

比原来贵一倍（原来每轮只测 8 个、轮转覆盖），换来的是**每个节点的读数都是新鲜的**——
选具体节点比选国家更依赖新鲜度，30 分钟前的读数可能已经过时。
省下的那点流量在 140GB/15 天的配额面前不值一提。

## 六、观察点：怎么判断有没有出问题

```bash
# 当前节点 + 带宽排名
ssh luyou 's=$(cat /etc/miniclash/api_secret); \
  curl -s -H "Authorization: Bearer $s" http://127.0.0.1:9090/proxies/自动优选 | grep -oE "\"now\":\"[^\"]+\""; \
  head -5 /tmp/miniclash_rank'
# 裁决历史（每次切换都有带宽数字）
ssh luyou 'tail -10 /etc/miniclash/judge.log'
# 故障自愈记录
ssh luyou 'tail -10 /etc/miniclash/guard.log'
```

| 现象 | 判断 |
|---|---|
| 节点数小时级不换 | 正常。带宽差小于 25% 就不该换 |
| 每 15 分钟换一次 | 噪声驱动或两个节点带宽接近 → 看 judge.log 里的带宽差值 |
| judge.log 里 `候选 X 1/2` 反复出现但不切 | 正常：双确认未满 |
| guard.log 频繁"当前节点不通" | 节点真在挂，或探活 URL 被它挡了 → 看排名里前几个节点是否都失败 |
| 探测累计每天涨 ~1.5GB | 正常 |

## 七、被否决的方案（别再翻出来）

- **国家组改 fallback + judge 指定节点**：fallback 组不吃 API 的 `PUT`，组内择优是空转
  （2026-10-24 实现留在分支 `feature/bandwidth-selection`，未部署）。
- **judge 测速与内核 url-test 用同一个 URL**：judge 每轮覆盖内核的延迟记录 → 组内每 5 分钟横跳
  （2026-10-15 事故）。现在没有内核 url-test 了，但 probe 与 guard 仍各用各的 URL，别合并。
- **只用 delay API 选节点**：测不出带宽，见上。
- **并发测速**：互抢带宽，排序失真。
