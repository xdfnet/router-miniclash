# 组内选优：国家 url-test 组怎么选节点

> 记录 2026-10-24 对「组内选谁」这件事的实测与结论。判据、参数值都写在这里，
> 改代码时同一次提交里改本文（文档与代码同源）。

## 一、机制：组内归内核管，脚本不插手

```
自动优选 (select)          ← judge 只对这一层发 PUT（跨国切换）
├── 日本组 (url-test)      ← 组内由 mihomo 内核全权决定
│   └── 日本1 … 日本8
└── 新加坡组 (url-test)
    └── 新加坡1 … 新加坡8
```

- **组内选谁 = 内核 url-test 组**。每 60s 对组内每个节点打一次 `github.com/generate_204`，
  按延迟排序，`now` 指向最快者；`tolerance: 200` 是切换门槛。
- **judge.sh 不碰组内**，它只对主组「自动优选」发一次 PUT 做跨国切换。
- **init.d 的 watchdog 只观察不驱动**：每 60s 把 select→国家组→节点这条链路展开，
  上报 `miniclash.core.node`。
- 节点失效时内核**立即**切到组内下一个存活节点（不等 interval），这是自愈能力所在，
  与 tolerance 无关。

相关参数（`root/etc/init.d/miniclash` 的 `gen_config()` 生成）：

```
{ name: 日本组, type: url-test, proxies: [日本1…日本8],
  url: 'https://github.com/generate_204', interval: 60,
  tolerance: 200, expected-status: 200/204 }
```

`expected-status: 200/204` 只认真实 204（generate_204 固定返回），防运营商劫持返回假 200
被误判为健康。

## 二、tolerance 语义

内核每轮测出全组延迟，最快者 `f`、当前选中者 `c`，仅当

```
f + tolerance < c      （新节点至少快出 tolerance 毫秒）
```

才切换。所以 tolerance 是**「切换迟钝度」旋钮，不是判据旋钮**——它决定内核多久乱跳一次，
不决定按什么挑节点。

2026-10-24 实测（路由器 v1.19.32，`/proxies/<节点>/delay`，URL 用 `github.com/robots.txt`
以免污染内核 url-test 的决策数据）：

| 样本 | 日本1 连续 6 次 |
|---|---|
| 延迟 | 664 / 769 / 345 / 891 / 656 / 348 ms |

同一节点单次采样跨度 **546ms**（最坏一次是真值的 3 倍）。取「多次最小值」当抗噪真值：

| 节点 | 日本3 | 日本2 | 日本1 | 日本4 | 日本5 | 日本8 | 日本7 |
|---|---|---|---|---|---|---|---|
| 真值延迟 | 332 | 347 | 351 | 353 | 366 | 482 | 740 |

## 三、为什么 tolerance = 200

两个数一起看才有意义：

- **噪声**：单次采样跨度 546ms，典型 ±100ms，尾部能到 +900ms。
- **真实差异**：组内前 5 个节点真值只差 **34ms**（332~366ms）。

| tolerance | 能识别「真慢节点」（日本7 领先 389ms） | 被噪声误切 |
|---|---|---|
| 500（旧值） | **否** → 等于锁死组内 | 几乎不 |
| **200（现值）** | 是 | 偶发（需采到 650+ 坏样本） |
| 100 | 是 | 频繁 |

500 门槛下，日本7（真值 740ms）要顶替日本1（真值 351ms）需领先 389ms，389 < 500 →
**连慢一倍的节点都换不掉**，组内形同虚设。200 既能识别真劣化，又不被 ±100ms 典型噪声带偏。

**改动记录**：2026-10-24 由 500 改为 200（commit `6097a90`）。

## 四、已知边界（别踩）

### 1. 内核 url-test 是单样本，判断可能反着来

内核每组只测一次，采到什么算什么。2026-10-24 上午内核记的 `history`：
日本3 = 2081ms、日本5 = 1584ms（判为最慢两节点），而实测真值分别是 **332ms（最快）** 和 366ms
——**内核把最好的节点当成了最差的**。噪声直接决定排序。

### 2. 延迟维度上，组内几乎不存在「最优节点」

前 5 个节点真值差 34ms，远小于噪声。tolerance 能做的只有「把明显慢的踢出去」，
**挑不出最优**。要按真实下载速度排序，得换判据（带宽），见第六节。

### 3. url-test 组和 fallback 组都不吃脚本指定

实测（mihomo v1.19.32）：

| 组类型 | `PUT /proxies/<组> {"name":"<节点>"}` 的效果 |
|---|---|
| select | **生效**，`now` 立刻跟随，流量同步改道 |
| url-test | 只写 `fixed` 字段，`now` 不变（`fixed` 内核不理会） |
| fallback | 同 url-test，无效 |

推论：**只有 select 组能被脚本指定节点**。而 select 组没有内核自愈——节点挂了不会自动降级，
得由脚本兜底（切换空窗 = judge 的执行间隔）。这就是「按带宽选组内节点」绕不开的取舍。

### 4. 组内切换会断连

url-test 换节点时在途连接重建、浏览器重连、缓存重建。2026-10-15 踩过同类坑
（judge 测速与内核 url-test 用同一 URL，judge 每轮覆盖内核的延迟记录 → 组内每 5 分钟横跳一次）。
所以 judge 刻意改用 `github.com/robots.txt` + `github.githubassets.com/generate_204`，
与内核的 `github.com/generate_204` 解耦。**任何新的测速手段都要保持这个解耦。**

## 五、观察点：怎么判断这次改动有没有带来误切

tolerance 从 500 降到 200，等于允许内核在噪声驱动下换出口。判断标准：

- **正常**：组内 `now` 长时间稳定（小时级不换）。
- **误切**：`now` 每分钟都在变 → 噪声驱动，把 tolerance 调到 300 或 400，**不要调回 500**
  （500 是形同虚设的）。

```bash
# 查当前 now 与 fixed
ssh luyou 'S=$(cat /etc/miniclash/api_secret); \
  curl -s -H "Authorization: Bearer $S" http://127.0.0.1:9090/proxies/日本组 \
  | grep -oE "\"(now|fixed)\":\"[^\"]*\""'
```

## 六、按带宽择优：方向对，但现有实现不可用

带宽维度区分度远大于延迟（实测同一批节点，带宽 30KB/s ~ 174KB/s，差 5.8 倍），
所以「延迟 ≠ 体验」的判断成立。但 2026-10-24 的第一版实现有三个硬伤，**不要直接用**：

| 硬伤 | 实测 |
|---|---|
| 16 路并发互抢带宽 | 并发测日本3 第一(174K)、串行测日本1 第一(226K)；日本5 并发 30K、串行 144K |
| 单次采样，噪声 55% | 日本3 连测三次 133K / 180K / 206K B/s |
| 128KB 样本被握手时间摊薄 | 日本3 测 128KB 得 133~206K，测 1MB 得 411K |

另有一个架构硬伤：要让 judge 决定组内节点，国家组必须换成能被 PUT 的类型
（见第四节第 3 条：只有 select 行），代价是失去内核自愈。

要重做这一块时，最小正确形态：**串行或低并发 + 每节点重复 3 次取中位数 + 样本放到 1MB 量级 +
切换门槛提到 50% 以上且只在明显优势时切**。

存档：改造版完整实现（含 `probe.sh`、fallback 改造、judge 接线）在分支
`feature/bandwidth-selection`（commit `08ce431`），未部署，仅供参考。
